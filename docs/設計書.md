# IT技術図鑑 設計書

## 0. この文書の読み方

これは、作り始める前に決めておくことを1本にまとめたものです。承認をいただいてから制作に入ります。

- **「わたしの判断」と書いた箇所**は、指示書に書かれていなかったため、こちらで決めたものです。変えたい場合は言ってください。
- **「未決」と書いた箇所**は、ご本人にしか決められないため、空けてあります。§20 にまとめてあります。
- **依頼の原文は `docs/指示書.md` に保存しました。** これまで会話の中にしかなく、セッションが失われれば設計の根拠が消える状態でした。原文は書き換えません。この設計書は、その原文に対する解釈と決定です。
- 文章は日本語で書きました。読むのが人だからです。AIだけが読む `CLAUDE.md` は英語にします(そのほうが正確に読まれます)。

## 1. なぜ作るのか

プログラミング未経験から初心者の日本人の大人が、IT技術を**人物・物語・意外性**の形で覚えられる読み物を作ります。

役目は2つあります。

1. **自分の勉強の整理** — 書いた人が読み返して使える
2. **社内の新人に渡す** — 初見の人が一人で読み通せる

この2つは同じものを求めます。どちらも「あとから1項目だけ足せる」構造と、「どのページも同じ形」であることを必要とします。

### なぜ図鑑の形なのか

用語集では覚えられません。「Gitはバージョン管理システムです」という説明は、読んだ瞬間に消えます。一方で「Gitという名前は、作者が自分を指して言った『嫌なやつ』というイギリスのスラングから来ている」は残ります。**残るのは、驚きと、人の顔と、話の流れです。** 図鑑の形は、誕生年・生みの親・出身地・名前の由来という枠を全ページに強制するので、書く側が自然とその4つを集めることになります。

## 2. 目標・目標でないこと・失敗

### 目標

- §16 の全分野に、最低1ページの図鑑ページがある
- 全ページが同じ構成で揃っている
- スマホ(375px)とPCの両方で快適に読める
- すべての事実に出典がつき、すべての画像にクレジットがある
- 新しい項目を、Markdownファイルを1つ足すだけで増やせる

### 目標でないこと

- 技術の網羅。載せないものがあってよい
- リファレンスとしての正確な仕様説明。それは公式文書の仕事
- 確認クイズ・フラッシュカード(指示書で明確に除外)
- 検索エンジンからの流入を増やすこと

### 失敗の定義(技術的に動いていても失敗とみなすもの)

- **ページごとに構成がばらつく。** 読者が毎回どこに何が書いてあるか探すことになり、中身に集中できなくなります
- **出典のない雑学が載る。** 面白い話ほど俗説が多く、出典がないと図鑑ごと信用を失います
- **項目を足すのにテンプレートの改造が必要になる。** そうなると項目が増えなくなり、図鑑として死にます
- **造語が増える。** 読者が実在しない言葉を覚えさせられ、覚える量が二重になります(2026-10-26 のご指摘)
- **AIのページが古い情報のまま残る。** 更新日を出すだけでは足りず、古いものを見つけられる必要があります

## 3. 読者と文体

| 項目 | 決めたこと |
|---|---|
| 読者 | プログラミング未経験〜初心者の日本人の**大人**。子ども向けの書き方はしない |
| 文体 | やさしい「です・ます」調 |
| 専門用語 | 初出時に一言で説明する。説明なしで使ってよいのは、そのページの主役である語だけ |
| 造語 | **作らない。** 分類名も地図の区画名も、実在する言葉だけを使う |
| たとえ話 | 使う。ただし**名前には使わず、本文の説明の中だけで使う**。例:地図のラベルは「Docker」、Dockerのページの本文で「船の輸送コンテナと同じ考え方です」と説明する |
| 1ページで覚えるポイント | 3つまで |
| 強調 | 1ページ1か所だけ。「今日のひとこと」に使う |

## 4. 制約

- **静的サイト**。サーバー側のプログラムを動かさない
- **1項目 = 1つのMarkdownファイル**。メタデータは冒頭の frontmatter に書き、図鑑カード・年表・相関図・世界地図に自動反映させる
- **図解はSVGで自作**。権利の心配がなく、スマホでも鮮明
- **写真は利用条件が明記されたものだけ**。各画像に撮影者・ライセンス・出典を表記
- **ロゴ・マスコット画像は使わない**。公式ページへのリンクにとどめる。マスコットを似せたイラストも描かない
- **雑学の文章は自分の言葉で書く**。他サイトの文章を転載しない
- 公開先は GitHub Pages、デプロイは GitHub Actions
- ダークモード対応、オフラインでも読める(PWA)、読んだ記録は localStorage
- 開発機は Windows 11。読者の環境も Windows を想定する(**わたしの判断**。社内の新人に渡すため)

## 5. 技術の選定

### 採用:Astro

指示書の推奨どおり Astro を使います。理由は3つです。

1. **Content Collections が、この図鑑の中心そのもの。** frontmatter の形を型で定義でき、違反していると**ビルドが失敗します**。「ページごとに構成がばらつく」という失敗を、文章の約束ではなく機械で止められます
2. **既定でJavaScriptをページに出さない。** 図鑑の大半は読み物なので、速度が素直に出ます。登録スタンプなど動きが必要な場所だけ島状にJavaScriptを置けます
3. Markdown、SVG、画像最適化、サイトマップ、PWA が公式または定番の拡張で揃っており、自分で組む部分がほとんどありません

### 検討して採らなかったもの

| 候補 | 採らなかった理由 |
|---|---|
| Eleventy | 動作は軽く十分だが、frontmatter の型検査が標準でない。「構成がばらつく」をビルドで止められない |
| Next.js | サーバー機能が主で、静的な読み物には重い。覚えることが増える |
| Hugo | 速いが、テンプレートの書き方が独特で、あとから手を入れる人(ご本人・新人)の負担が大きい |
| VitePress / Docusaurus | 技術文書向けの型が強く、図鑑カードや町の地図のような独自の見た目に抗う |
| 手書きHTML | 項目を足すたびに同じHTMLを複製することになり、「1ファイル足すだけ」が崩れる |

### 使うもの一覧

| 用途 | 使うもの | 備考 |
|---|---|---|
| サイト生成 | Astro(安定版) | — |
| 本文の形式 | **MDX**(`.mdx`) | 図解SVG・写真・出典をコンポーネントで本文に差し込むため。素の `.md` では import できない |
| frontmatter の型検査 | Astro Content Collections + Zod | 違反でビルド失敗 |
| PWA・オフライン | `@vite-pwa/astro` | 全ページを事前キャッシュ |
| 画像最適化 | `astro:assets` | WebP 変換・遅延読み込み |
| サイトマップ | `@astrojs/sitemap` | — |
| 図解 | 手書きSVG(ライブラリなし) | CSS変数で色を受け、ダークモードに追従 |
| レーダーチャート | 手書きSVG(ライブラリなし) | 3軸なので三角形。ライブラリを入れる価値がない |
| リンク切れ検査 | `lychee` または `linkinator`(CI) | — |
| 構成の検査 | 自作の検査スクリプト1本 | §8 の機械検査 |
| Node | LTS版 | `.nvmrc` に固定 |

## 6. サイトの構成

```
/                     町の地図(トップ)
/zukan/               図鑑一覧(タイプで絞り込み、名前で絞り込み、更新が古い順も選べる)
/zukan/<slug>/        各項目のページ(例 /zukan/git/)
/nenpyo/              年表(1947年のバグから現在まで一本の線)
/hitobito/            人物相関図
/sekai/               世界地図(出身地にピン)
/jiken/               やらかし事件簿(年表形式・内容と教訓)
/aruaru/              エンジニアあるある
/slang/               ネットスラング辞典
/kakugen/             名言・格言集
/gokai/               よくある誤解まとめ
/nihon/               日本発の技術コーナー
/credit/              画像クレジット一覧(自動生成)
/about/               この図鑑について(方針・出典の扱い・更新日の意味)
```

ランダム豆知識は独立ページを作らず、町の地図とページ下部に置くボタンにします(**わたしの判断**。1行の雑学のために1ページ遷移させる価値がないため)。

### サイト内検索(**わたしの判断**)

**専用の検索ページは作りません。** 35ページに全文検索(Pagefind など)を入れるのは過剰で、索引ファイルがPWAのキャッシュを膨らませます。代わりに、図鑑一覧ページに**名前・読み方・別名で絞り込む入力欄**を1つ置きます。ビルド時に小さなJSONを作り、クライアント側で絞り込みます。これで frontmatter の `aliases`(「ギット」と打っても Git に当たる)が働きます。将来ページ数が100を超えたら全文検索を検討します。

### 画面の作り

| 幅 | 形 |
|---|---|
| スマホ(〜767px) | 1カラム。目次は見出し直下の折りたたみ |
| PC(768px〜) | 本文 + 左に目次サイドバー(H2から自動生成、現在位置を追従) |

## 7. タイプ(分類)

6つです。1項目に1つだけ割り当てます。

| 内部の記号 | 画面に出る名前 | 中身 | 色(ライト/ダーク) |
|---|---|---|---|
| `language` | 言語タイプ | HTML、Python など | 青 `#2563eb` / `#7aacff` |
| `tool` | ツールタイプ | Git、VS Code、PowerShell など | 橙 `#c2410c` / `#ff9d63` |
| `ai` | AIタイプ | ChatGPT、Claude Code など | 紫 `#7c3aed` / `#b79bff` |
| `place` | 場所タイプ | Linux、Docker、クラウド、GitHub | 緑 `#047857` / `#45d6a4` |
| `mechanism` | しくみタイプ | HTTP、API、フレームワーク | 赤 `#be123c` / `#ff8098` |
| `data` | データタイプ | SQLite、MySQL | 黄土 `#a16207` / `#e0b44a` |

**内部の記号は英語、画面の名前は日本語**に分けて持ちます。表示の言葉を変えたくなったとき、Markdownファイルを書き直さずに1か所で直せるようにするためです。

**色だけに頼りません。** どのタイプかは必ずバッジの文字でも示します。色の見分けがつきにくい人でも区別できる必要があるためです。

## 8. frontmatter の仕様

これがこの図鑑の背骨です。ここに書いた値が、図鑑カード・年表・相関図・世界地図・クレジットページに自動で流れます。

```yaml
---
# ---- 必須 ----
no: 4                        # 図鑑番号。整数。重複するとビルド失敗
name: Git                    # 表示名
reading: ギット               # 読み方
type: tool                   # language | tool | ai | place | mechanism | data
oneLine: 書いたものを、いつでも昔の状態に戻せるようにする道具。
surprise: >                  # 冒頭の「意外な一文」
  Gitという名前は、作者が自分を指して言ったイギリスのスラングで、
  「嫌なやつ」という意味です。
takeaway: >                  # ページ末尾の「今日のひとこと」。ここだけ強調される
  保存ボタンではなく、「戻れる印」を自分で打つ道具です。
status:                      # レーダーチャート。1〜5の整数
  difficulty: 3              #   難易度
  popularity: 5              #   人気
  breadth: 4                 #   活躍場所の広さ
order: 30                    # 学ぶ順の並び。整数
updated: 2026-10-26          # 更新日。ページに「この内容は○年○月○日時点」と出る

# ---- 任意。無ければその欄をカードに出さない ----
born: 2005                   # 誕生年(西暦)
bornNote: 開発開始も2005年     # 補足(「開発開始は1989年」など)
creators:
  - name: リーナス・トーバルズ
    nameEn: Linus Torvalds
    wikidata: Q44968         # 人物相関図で同一人物をまとめる鍵
birthplace:
  label: アメリカ
  lat: 37.77
  lng: -122.42               # 世界地図のピン。省くとピンが立たない
mascot:
  name: なし
  origin: 公式ロゴのみ
officialUrl: https://git-scm.com/
aliases: [ギット]              # 検索用の別名
related:                     # 相棒・ライバル
  - slug: github
    relation: partner        # partner | rival | ancestor | descendant
    note: Gitを人に見せる場所
sources:                     # 出典。本文から [^1] の形で参照する
  - id: 1
    title: Git公式サイト About
    url: https://git-scm.com/about
    accessed: 2026-10-26
images:                      # このページで使う写真。idを本文から参照
  - id: linus
    file: linus-torvalds.jpg
    caption: リーナス・トーバルズ
    author: 撮影者名
    license: CC BY-SA 3.0
    licenseUrl: https://creativecommons.org/licenses/by-sa/3.0/
    source: https://commons.wikimedia.org/wiki/File:...
disputed: false              # 諸説ある話を含むなら true。注記が自動で出る
draft: false                 # true の間は本番に出ない
---
```

ファイル名がURLになります。`src/content/zukan/git.md` → `/zukan/git/`。半角英小文字とハイフンだけを使います。

### 書くときに機械が止めること

守らせたいことは、文章の約束ではなく検査で止めます。書いておくだけの決まりは破られるからです。

| 止めること | どう止めるか |
|---|---|
| frontmatter の必須項目が無い、型が違う、`no` が重複している | Content Collections の型検査。ビルド失敗 |
| 決まった見出しが足りない、順番が違う | 自作検査スクリプト。ビルド失敗 |
| 本文の `[^n]` に対応する `sources` が無い。逆に使われていない出典がある | 同スクリプト |
| 本文が参照している画像が `images` に登録されていない、クレジット欄が空 | 同スクリプト |
| 強調が1ページに2か所以上ある | 同スクリプト |
| 図解が1枚もない | 同スクリプト |
| リンク切れ | CIでリンク検査 |
| 事実が正しいか | 機械では無理。出典があることまでしか機械は見られない |

最後の行は正直に書いておきます。**出典が付いていることは機械が保証できますが、その出典が正しいかは人が確かめるしかありません。**

## 8-2. データの持ち方(コレクション構成)

図鑑ページだけでは、年表の「1947年のバグ」や、あるある・スラング・格言を置けません。コレクションを**3つ**に分けます(**わたしの判断**)。人物は4つ目を作らず、図鑑の `creators` から導きます。

| コレクション | 置き場所 | 1件が何か | どのページに出るか |
|---|---|---|---|
| `zukan` | `src/content/zukan/*.mdx` | 技術1項目 | 図鑑ページ、町の地図、年表(`born` の年)、世界地図、相関図 |
| `events` | `src/content/events/*.md` | 出来事1件 | やらかし事件簿、年表 |
| `notes` | `src/content/notes/*.md` | 短い読み物1件 | あるある、スラング辞典、格言集、誤解まとめ、日本発コーナー、ランダム豆知識 |

全体ページも**1ファイル足すだけで増えます**。図鑑と同じ方針です。

### `events`(出来事)

```yaml
---
year: 1947                   # 必須。年表と事件簿の並び
date: 1947-09-09             # 任意。日付が分かるなら
title: 作業記録に蛾が貼られた
kind: origin                 # origin（由来・はじまり） | incident（障害・事件） | milestone（節目）
summary: グレース・ホッパーのチームが、不具合の原因だった蛾を作業記録に貼りつけた。
lesson: >                    # kind が incident のとき必須。教訓として書く
  記録を残すことが、原因を突き止める最初の一歩になります。
related: [git, linux]        # 任意。関係する図鑑項目の slug
sources: [...]               # 図鑑と同じ形
updated: 2026-10-26
---
```

- **年表(`/nenpyo/`)は `zukan` の `born` と `events` の `year` を混ぜて1本の線に並べます。** 技術の誕生と出来事が同じ線に乗るので、「Gitが生まれた2005年の前後に何があったか」が見えます
- **事件簿(`/jiken/`)は `kind: incident` の `events` だけを年表形式で出します。** 同じデータを2つのページが違う切り口で見せる形にして、同じことを二度書きません

### `notes`(短い読み物)

```yaml
---
category: aruaru             # aruaru | slang | kakugen | gokai | nihon | zatsugaku
title: エンジニアの「ちょっと見てもらえますか」は1時間かかる
body: …                      # 本文は Markdown
truth: …                     # category が gokai のとき必須。俗説に対する真実
related: [git]               # 任意
sources: [...]
updated: 2026-10-26
---
```

`category` でページを振り分けます。ページを増やしたくなったら `category` を1つ足すだけで済みます。

### 人物相関図(`/hitobito/`)の線の引き方

人物のコレクションは作りません。`zukan` の `creators` から機械的に組み立てます(**わたしの判断**。人物データを別に持つと、図鑑側と必ず食い違います)。

| 線 | 何から引くか |
|---|---|
| 人 — 技術 | その人が `creators` に入っている項目 |
| 人 — 人 | 同じ項目を一緒に作った(`creators` が2人以上) |
| 技術 — 技術 | `related`(`partner` / `rival` / `ancestor` / `descendant`) |

同じ人を1つにまとめる鍵は `creators.wikidata` です。表記が「リーナス・トーバルズ」と「Linus Torvalds」で揺れても、同じ人として扱えます。**`wikidata` が無い人は、別人として扱われます。** 複数の項目に登場する人には必ず付けます(検査スクリプトが、2回以上出てくる名前に `wikidata` が無ければ警告します)。

## 9. 1ページの構成

指示書の17項目をそのまま、固定の順で並べます。見出しは問いの形にします。

| # | ブロック | 中身 | 無いとき |
|---|---|---|---|
| 1 | 意外な一文 | `surprise` から自動 | 必須 |
| 2 | 図鑑カード | frontmatter から自動。名前・読み方・タイプ・ひとことで・誕生年・生みの親・出身地・マスコット・レーダーチャート | 必須 |
| 3 | 誕生物語 | 困りごと → 発明 → その後 の三幕。見出しは問いの形 | 必須 |
| 4 | 名前の由来 | 目玉コーナー | 必須 |
| 5 | たとえ話 | 本文内で使う。名前には使わない | 必須 |
| 6 | 図解 | 最低1枚。説明文のすぐ隣 | 必須 |
| 7 | 写真 | 生みの親や歴史的な物 | 使える画像が無ければ省略 |
| 8 | 得意技 | 最初に覚えるコマンドや書き方を3つまで | 必須 |
| 9 | あなたとの関係 | 読者の身近な体験とのつながり | 必須 |
| 10 | ネットでの扱われ方 | ミーム、あるある、ネタ | ネタが無ければ省略 |
| 11 | やらかし事件簿 | 該当する有名な出来事。教訓として書く | 該当が無ければ省略 |
| 12 | よくある誤解 | 俗説と真実 | 該当が無ければ省略 |
| 13 | 相棒・ライバル | `related` から自動でリンク | 必須 |
| 14 | 最初の一歩 | 今日5分でできること | 必須 |
| 15 | 無料教材 | 外部リンク。完全無料を優先し、一部有料は明記 | 必須 |
| 16 | 今日のひとこと | `takeaway` から自動。**ページ内で唯一の強調** | 必須 |
| 17 | 出典 | `sources` から自動生成 | 必須 |

省略可のブロックは、中身が無ければ見出しごと出しません。空の見出しが並ぶほうが読者を迷わせるためです(**わたしの判断**)。

1・2・13・16・17 は frontmatter から**自動で描かれます**。書き手が本文に書くのは 3〜12・14・15 だけです。

### ブロックの印(**わたしの判断**)

見出しの文言は固定できません。「見出しは問いの形にする」という決まりがあり、ページごとに文言が変わるためです。かわりに、各ブロックの直前に**印のコメント**を置きます。HTMLコメントなので、出来上がったページには出ません。

```mdx
{/* block: birth */}
## なぜGitは「嫌なやつ」という名前なのか？

2005年の春、リーナス・トーバルズは困っていました。…
```

| 印 | ブロック | 必須か |
|---|---|---|
| `birth` | 3 誕生物語 | 必須 |
| `naming` | 4 名前の由来 | 必須 |
| `analogy` | 5 たとえ話 | 必須 |
| `figure` | 6 図解 | 必須 |
| `photo` | 7 写真 | 省略可 |
| `skills` | 8 得意技 | 必須 |
| `you` | 9 あなたとの関係 | 必須 |
| `internet` | 10 ネットでの扱われ方 | 省略可 |
| `incident` | 11 やらかし事件簿 | 省略可 |
| `misunderstanding` | 12 よくある誤解 | 省略可 |
| `firststep` | 14 最初の一歩 | 必須 |
| `materials` | 15 無料教材 | 必須 |

検査スクリプトは、本文に現れた印を順に取り出し、**必須が全部あるか、順番が表のとおりか**を見ます。違っていればビルドを止めます。見出しの文言は自由なまま、構成だけを機械で守らせられます。

### 本文に書ける部品

本文に置けるのはこの3つだけです。覚えることを増やさないためです。

| 部品 | 書き方 | 何をするか |
|---|---|---|
| 図解 | `<Figure name="git-branch" caption="枝が分かれて、また合流します" />` | `src/components/figures/git-branch.astro` のSVGを差し込む |
| 写真 | `<Photo id="linus" />` | frontmatter の `images` から、画像とクレジットを一緒に描く |
| 出典 | `<Cite n={1} />` | frontmatter の `sources` の `id: 1` を指す上付き番号。クリックで出典へ飛ぶ |

**標準のMarkdown脚注(`[^1]`)は使いません。** 脚注は自分で番号と注釈欄を作るので、frontmatter の `sources` から自動生成する出典欄と番号が二重になります。§8 の frontmatter 例にある `[^1]` という書き方は、この `<Cite n={1} />` に読み替えてください。

### 強調の決まりを機械で守らせる方法(**わたしの判断**)

「強調は1ページ1か所」を検査できる形にします。

- **色や大きさを変える強調は、`takeaway`(今日のひとこと)の自動描画だけです。** 本文側に強調用の部品を用意しません。無いものは使えません
- 本文の `**太字**` は、色も大きさも変えないCSSにします。語を目立たせたい用途は残しつつ、「1ページ1か所」の決まりには触れません
- 検査スクリプトは、本文に強調用の部品が無いこと、`takeaway` がちょうど1つあることを見ます

### 図解があることの検査

本文に `<Figure` が1つ以上あることを見ます。`name` で指したSVGファイルが実在することも確かめます。

### 再会させるしかけ

指示書の「別のページで同じ人物・話題をさりげなく再登場させる」は、`related` のリンクとは別の仕掛けです。本文中にそのまま書きます(例:Dockerのページに「中身はLinuxです。ペンギンのTuxを覚えていますか?」)。機械では検査できないので、各ページを書くときの手順に入れます(§17)。

### 更新日の扱い

- frontmatter の `updated` を、図鑑カードの右下に小さく「この内容は2026年10月26日時点」と出します
- 強調はしません。強調は「今日のひとこと」1か所だけという決まりがあるためです
- 図鑑一覧ページで**更新が古い順に並べ替えられる**ようにします。更新日を出すだけでは「古いものを見つける」ができないためです
- 情報が古いかどうかの最終判断は読者に委ねます(2026-10-26 のご指示)

#### AIタイプだけ扱いが違う点(**わたしの判断**)

先の版で「AIのページは更新日の扱いが他と違う」と書きながら、どう違うかを書いていませんでした。決めます。

タイプごとに**古いとみなす日数**を持たせます。設定は1か所(`src/config.ts`)です。

| タイプ | 古いとみなす日数 | 理由 |
|---|---|---|
| AI | **180日** | できることや料金が半年で変わります |
| その他すべて | なし | Gitの誕生年は古くなりません |

日数を超えたページには、図鑑カードの更新日の隣に「情報が古い可能性があります」という小さな注記が自動で出ます。色も大きさも変えません(強調は1ページ1か所の決まりがあるため)。図鑑一覧では、超えたページに同じ印が付き、絞り込めます。

**これは警告であって、非公開にはしません。** 古いかどうかの判断は読者に委ねるというご指示に沿い、材料だけを出します。

## 11. 図鑑登録システム

- 読んだページに「登録済み」スタンプ。記録は localStorage
- **何をもって「読んだ」とするか(わたしの判断)**:ページ末尾の「今日のひとこと」が画面に入った時点で、自動的に登録済みにします。ボタンを押させる形は採りません。押し忘れが積もると登録率が実態と合わなくなり、「12/35種 発見」という数字が意味を失うためです。開いただけで登録する形も採りません。それでは「読んだ記録」になりません
- 登録を自分で取り消せるようにします。読み直したいページを戻せる必要があるためです
- トップに登録率、タイプ別の内訳
- **localStorage が使えない環境でも表示が壊れないようにします。** 読み取りと書き込みを例外処理で囲み、使えなければ「未登録」のまま表示します。プライベートウィンドウやストレージを止めている環境では読めないためです
- サーバーに送りません。端末ごと・ブラウザごとの記録です。その旨を `/about/` に書きます

- **React・Flask・Djangoは「しくみ」。** 言語ではなく、言語の上に乗る決まりごとだからです
- **セキュリティは「しくみ」。** 道具でも場所でもないため
