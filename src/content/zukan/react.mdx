## なぜ「書き換える」のをやめたのか？

昔のやり方では、画面の一部を直接書き換えていました。「この数字を3に変える」「この行を消す」と、手順で指示します。

画面が複雑になると、これが破綻します。どこをいつ書き換えたかが追えなくなり、「なぜかここだけ古い値のまま」という不具合が起きます。

React が持ち込んだのは別の考え方でした。**いまの状態なら、画面はこうなるはず**と書く。差分の計算は道具側がやる<Cite n={1} />。人は手順ではなく、あるべき姿を書きます。

2013年に Facebook（現 Meta）が公開しました<Cite n={2} />。この考え方は広く真似され、いまでは画面作りの標準的な発想になっています。

{/* block: naming */}
## 名前の由来：反応する

react は「反応する」です。状態が変われば、画面がそれに**反応して**あるべき姿に変わる。その振る舞いがそのまま名前です。

ロゴは原子の模型です。電子が原子核の周りを回る、あの図です。小さな部品（コンポーネント）が集まって画面ができている、という考え方を表しています。

{/* block: analogy */}
## たとえ話：指示書ではなく、完成図を渡す

模型を作るときに「3番の部品を2番にはめて、次に5番を…」と手順で指示するのが昔のやり方です。

React は完成図を渡します。「完成形はこれです」と。いまの形と完成図を見比べて、違うところだけ直すのは道具の仕事です。

完成図は書きやすく、読みやすい。手順書は、途中で誰かが別の手順を挟むと壊れます。

## 最初に覚える3つ

| 言葉 | 意味 |
|---|---|
| コンポーネント | 画面の部品。これを組み合わせて画面にする |
| 状態（state） | いまの値。これが変わると画面が変わる |
| props | 親の部品から子の部品へ渡す値 |

2つめが核心です。「状態を変えれば画面が追いつく」という一方向の流れを飲み込めれば、React の考え方はほぼ理解できています。

{/* block: you */}
## あなたとの関係

あなたが毎日使っているWebサービスの多くが、これで作られています。入力した瞬間に候補が出る、ボタンを押すと一部だけ変わる、といった画面です。

業務システムの画面を作る案件でも、まず候補に挙がります。名前を知っておくと、見積書や提案書が読めるようになります。

{/* block: misunderstanding */}
## よくある誤解：React を使えばサイトが速くなる

速くなるとは限りません。React 自体の部品を読み込むぶん、単純なページなら素の HTML のほうが速いです。

React が効くのは、画面の変化が複雑な場合です。文章を読ませるだけのページに使うと、重くなるだけということもあります。このサイトが React を使っていないのは、そのためです。

## 今日5分でできること

公式サイトに、ブラウザ上で動かせる入門があります。まず「状態を1つ変えると、画面のどこが変わるか」だけを見てください。

書き方を覚える必要はありません。「状態が主で、画面が従」という向きだけ掴めれば十分です。
