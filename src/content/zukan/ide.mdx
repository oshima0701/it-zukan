## なぜ道具をひとつにまとめる必要があったのか？

昔は、プログラムを作る作業が道具ごとに分かれていました。文字を書く道具で書き、別の道具で組み立て、動かして、間違いが出たらまた別の道具で調べる。そのたびに画面を切り替え、ファイルを保存し直します。

この行き来そのものが時間を食っていました。そこで「ひとつの画面の中で全部やれるようにしよう」という製品が現れます。最初のIDEとされるのは、1975年の Maestro I です<Cite n={1} />。パソコンが家庭に入る前の話です。

いまIDEが当たり前になったのは、機能が増えたからではありません。**行き来が減ったぶん、考えが途切れなくなった**からです。

{/* block: naming */}
## 名前の由来：Integrated は「組み合わさった」

IDE は Integrated Development Environment の頭文字で、日本語では統合開発環境と訳されます<Cite n={1} />。

大事なのは最初のI、Integrated（統合された）です。Development（開発）でも Environment（環境）でもなく、**統合されていること**がこの言葉の中身です。機能がいくつあるかではなく、それらが一か所に組み合わさっているかどうかが、IDEと呼べるかどうかの分かれ目です。

{/* block: analogy */}
## たとえ話：工具箱と作業台

エディタは、よく切れるカッターナイフです。切ることについては申し分ありません。

IDEは作業台です。カッターも、物差しも、万力も、明かりも、ゴミ箱も、手を伸ばせば届く位置に固定されています。カッター単体より場所を取り、使い始めるまでに少し手間がかかります。そのかわり、作業中に道具を探して立ち上がる必要がありません。

どちらが優れているという話ではなく、作るものの大きさで決まります。

## 最初に覚える3つ

IDEと名乗る道具には、たいていこの3つが入っています。名前だけ知っておくと、どの製品でも探せます。

| 機能 | 何をするか |
|---|---|
| 補完 | 打ちかけの続きを候補で出す |
| デバッガ | 動きを途中で止めて、中身を覗く |
| 定義へ移動 | その名前が書かれた場所へ飛ぶ |

2つめのデバッガが、エディタとの差がいちばん出るところです。プログラムを途中で止めて、そのときの値を見られます。「なぜか動かない」を、推測ではなく現物で調べられるようになります。

{/* block: you */}
## あなたとの関係

Excelのマクロを書く画面を開いたことがあれば、それも小さなIDEです。書く欄があり、実行ボタンがあり、止めて中を見る機能があります。

「開発環境」という言葉に身構える必要はありません。やることが一か所にまとまっている画面、というだけです。

{/* block: misunderstanding */}
## よくある誤解：VS Code はIDEではない

はっきり分かれていません。VS Code は小さなエディタとして出発しましたが、拡張を足していくと補完もデバッガも定義への移動も手に入ります。そうなると、IDEとの差は言葉の問題になります。

公式にも「エディタ」と名乗っていますが、現場での使われ方はIDEに近いことが多い。この線引きにこだわる実益はほとんどありません。

{/* block: firststep */}
## 今日5分でできること

いま使っているエディタで、「定義へ移動」に当たる機能を探してみてください。VS Code なら、名前の上で `F12` です。

飛べたなら、それはもうIDEに近い働きをしています。
